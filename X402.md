# x402 paywall demo

An agent is given a task it cannot complete and a spending ceiling. It hits a paywall,
reads the price, decides for itself, pays on-chain, and uses what it bought. No human
approves the payment.

```bash
npm run x402:merchant     # terminal 1 — serves the paywalled resource
npm run x402:agent        # terminal 2 — the agent
```

| Piece | File |
|---|---|
| Merchant: one resource behind HTTP 402, price 0.05 RLUSD | `x402-merchant.mjs` |
| Agent: ceiling 0.10 RLUSD, decides and pays | `x402-agent.mjs` |
| Vendor helper from `https://hackathon.ap4m.build/sdk/` | `ap4m-x402.mjs` |

## Two changes to the vendor helper

`ap4m-x402.mjs` came from the service. Two edits were needed to make it run here; both
are marked with a comment in the file.

1. **`save()` fsync on a directory.** Windows returns `EPERM` when `fsync` is called on a
   directory handle, which crashed the agent after it had signed the voucher but before it
   sent it. The directory fsync is now tolerant of `EPERM`/`EINVAL`; the `rename` above it
   is already atomic on Windows.
2. **Verify after inclusion, not after submit.** The Merchant submitted the redemption and
   verified it in the same breath. The RPC can still answer "unknown transaction" for one it
   has only just accepted, and the verifier reads that as `Merchant redemption transaction
   does not match payment` — so the Merchant returned HTTP 503 and served nothing, *after*
   the agent's money had already moved. It now waits for one confirmation before verifying.
   The transaction hash is persisted before the wait, so a crash in between is still
   reconciled through the retained payment on retry.

Two `console.error` lines were also added to the Merchant's two silent `catch` blocks.
The handler swallowed every internal error into a bare 503, which is what made both
failures above take so long to find. They print only on failure.

A third thing is configuration, not a patch: `createX402Merchant` needs a `submitter`
signer with gas. Without it the Merchant throws inside the handler and answers 503 with
`payment_pending_or_unavailable`, which says nothing about the cause. The Merchant's own
wallet is used, so the Agent's key never leaves the Agent.

## What this cost to find out

0.05 RLUSD was redeemed on an attempt whose Merchant state was deleted before the payment
could be replayed, so that one was paid for and never delivered. Three redemptions of
0.05 RLUSD happened in total on channel `0x6d824358…`; one delivered on a retry, one
delivered first pass, one was orphaned. Do not delete `.x402-merchant-state/` while a
payment row is incomplete — the retained payment is the only way the agent gets what it
paid for.

## Operational notes

- `.x402-merchant-state/merchant.lock` is left behind when the process is killed rather
  than interrupted. If no Merchant is running, delete the lock — never `merchant.sqlite`.
- Give each purchase a new `operation` name. An unresolved purchase must be resumed with
  its original arguments: `node x402-agent.mjs <operation>`.
- The resource content is canonical JSON, which admits only safe integers. Rates are
  therefore percent and positions are tenths, with the unit in the key name.
- A Merchant reached from another machine needs HTTPS. This one binds `127.0.0.1`.
