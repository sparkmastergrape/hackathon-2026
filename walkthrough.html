AP4M Walkthrough

What we built, how to run it, and what to say while it runs. Read this once before demoing; the commands are set apart so you can find them at a glance.

The one-sentence version

An autonomous agent holds its own wallet, signs a payment voucher without a human in the loop, redeems it against a settlement contract, and the money lands in a merchant wallet — and anyone can verify that it happened without trusting us or the payment service.

There are two demos. The first drives the payment directly through the SDK. The second is the one to lead with: the agent is given a task it cannot finish and a spending limit, walks into an HTTP 402, reads the price, decides on its own, pays, and uses what it bought.

The pieces

Pays Agent wallet Signs every voucher. Holds XRP for gas.
Holds funds Escrow vault Our 20 RLUSD budget sits here.
Records PaymentLedger Verifies the signature, emits the claim.
Receives Merchant wallet Gets the RLUSD. Ours, not a pool.

Two wallets, and they must be different addresses — AP4M rejects a setup where the party authorising a payment is also the party receiving it. That separation is the point, not a formality.

In demo 1 the agent submits the redemption, so only it needs gas. In demo 2 the merchant submits its own redemptions and pays for them — it holds about 78 XRP. The agent's key never goes near the merchant process; the agent only ever signs.

Before you demo

One command. It spends nothing and changes no chain state, so it is safe to run in front of people — and it catches every setup problem we hit today:

npm run predemo

Twelve checks across three groups: that .env holds the keys and is git-ignored, that the agent key matches the address AP4M has registered and has gas, and that the service is up and our team still authenticates. It ends in one word.

GO  — all 12 checks passed. Run: node run-ap4m.cjs

Anything else prints NO-GO and lists exactly which checks failed and why. If it says NO-GO, do not start the demo. Fix what it names — re-running without changing anything will not help.

The two underlying checks still exist on their own if you want to narrow a problem: node verify-wallets.mjs for keys, gas and addresses, and node signin-check.cjs for the service side.

It does not cover demo 2. For the x402 run, do one rehearsal pass end to end before the room fills — start the merchant, buy once, confirm you see redemption Confirmed — and leave the merchant running afterwards.

Check the gas before you stand up

Each full run costs roughly 0.0003 XRP. The agent had about 20 XRP, which is hundreds of runs — but the faucet is rate-limited and slow during the event, so top up the night before rather than in the room.

Demo 1 — the SDK path

node run-ap4m.cjs

One command, six steps, about twenty seconds. It pays 0.01 RLUSD by default — set PAYMENT_RLUSD in .env to change it. Each run opens a fresh channel and closes it at the end, so you can run it repeatedly without cleanup.

What to say while it runs

1 — Sign in

The agent wallet signs a one-time challenge. No password, no API key issued by a human.

"The agent authenticates as itself. Nobody logged in for it."

2 — Open a channel

One on-chain transaction to the vault, with a spending cap of 5 RLUSD.

"This is the agent's allowance. It cannot spend past the cap, whatever it decides to do."

3 — Sign and redeem a voucher

An EIP-712 typed signature over the channel and a running cumulative total, submitted to the PaymentLedger.

"The signature is bound to this chain and this contract, so the same voucher cannot be replayed somewhere else."

4 and 5 — Report and settle

The service releases RLUSD from the vault to our merchant wallet and publishes a receipt.

"The money has moved. Here is the receipt — and we don't have to take their word for it."

6 — Close the channel

The agent signs a final checkpoint and the channel closes.

"The allowance is withdrawn. Nothing is left open."

Demo 2 — the x402 paywall

This is the autonomy demo. A merchant sells one measured dataset the agent cannot produce for itself. The agent is told what to report and given a ceiling, and nothing else — no price, no approval, no human in the loop.

Asks Agent Ceiling 0.10 RLUSD per purchase.
Refuses HTTP 402 Quotes 0.05 RLUSD in a signed challenge.
Decides Agent Under the ceiling, so it signs and pays.
Releases Merchant Redeems on chain, then serves the data.

Two terminals. Start the merchant first and leave it running:

npm run x402:merchant     # terminal 1
npm run x402:agent        # terminal 2

The agent prints each decision as it makes it, so the audience watches the reasoning rather than a spinner. About fifteen seconds.

What to say while it runs

1 — The agent asks for something it cannot have

A plain GET with no payment attached. The merchant answers 402 Payment Required with a price and a channel binding.

"It just got told no. Nobody is going to tell it what to do about that."

2 — It decides for itself

The quoted 0.05 RLUSD is under the agent's standing 0.10 ceiling, so it pays. Above the ceiling it would refuse — the limit is the whole mandate.

"That's the only instruction it has: a budget. No approval step, no confirmation dialog."

3 — It pays and gets the data

The agent signs a voucher, the merchant redeems it against the PaymentLedger and releases the resource in the same request.

"One HTTP round trip, and a real settlement happened inside it."

4 — It uses what it bought

The last line of output names the weakest surface in the dataset. That sentence is not in the code anywhere — it only exists because the purchase succeeded.

"It couldn't have written that line without buying the data. That's the point of the whole thing."

If a judge asks "what stops it overspending?" — show them

Start the merchant priced above the ceiling and run the agent again:

MERCHANT_PORT=8412 RESOURCE_PRICE_RLUSD=0.50 \
  MERCHANT_STATE_DIR=./.refusal-merchant-state npm run x402:merchant

MERCHANT_PORT=8412 AGENT_CEILING_RLUSD=0.10 \
  AGENT_STATE_DIR=./.refusal-agent-state node x402-agent.mjs refusal-demo

The agent reads the price, refuses, signs nothing and exits 3. Two layers refuse independently — the agent's own check and the SDK's maximumAmount, the second still refusing when the first is skipped. Both land before a voucher exists.

node refusal-witness.mjs after <channel> <label> then shows the chain unchanged: same redemption count, no new claim IDs. The refusal leaves no trace because nothing happened.

It holds one base unit from the limit. At 100000000000000001 base units against a ceiling of 100000000000000000, both layers still refuse. At exactly the ceiling it buys, and settles for precisely that amount — so the comparison is > and the ceiling is inclusive. If a judge asks whether the limit is spendable: yes, to the base unit.

Three payments ran on the one open channel 0x6d824358…, taking its cumulative total from 0 to 0.15 RLUSD. That is the micropayment case the first demo never exercised: one channel, many vouchers, one on-chain cap.

The verification half

This is the part worth the most in judging, because it is the part that does not require trusting anyone. Open the receipt trail — it puts AP4M's claims beside the ledger's own emitted events and shows them matching.

To do it live instead, with the judge choosing the node:

RPC_URL=<their node> node verify-receipt-onchain.mjs <redemption tx>

It confirms the transaction succeeded, that it went to the PaymentLedger, decodes the claim and channel IDs out of the event log, and finds the RLUSD transfer into the merchant wallet in the surrounding blocks.

The line that lands

"The receipt isn't us telling you we paid. It's the ledger telling you, and you can read it from a node we've never touched."

Traps — read these before demoing

Portal identifiers are claim IDs, not transaction hashes

The identifiers under Payments and receipts return null from eth_getTransactionByHash. Pasting one into a block explorer on stage gives you an empty page and looks like a failed payment. Use the transaction hashes from the agent wallet's history instead.

MetaMask exports private keys without the 0x prefix

Pasted straight into .env, the key is rejected as invalid — which reads like the wrong key rather than a formatting problem. Prefix it.

AP4M's own config points at a faucet that does not exist

/public/config advertises faucet.testevm.ripple.com, which returns NXDOMAIN. The working one is faucet.xrplevm.org. Worth mentioning to the organizers — it is costing every team the same half hour.

Gas and the payout wallet are two separate blockers

Funding the agent is not enough. requestChannel() binds a merchant payout when it opens, so the payout wallet must be registered on the portal first or the run fails at step 2.

Every x402 merchant failure is the same silent 503

The merchant swallows each internal error into 503 payment_pending_or_unavailable, which says nothing about the cause. Two different defects wore that same mask for an hour. We added error logging to the merchant's two catch blocks — if it 503s on stage, look at terminal 1, not at the agent.

Do not delete the merchant state directory after a failure

A payment the merchant has retained but not completed is the only way the agent gets what it already paid for. Wiping .x402-merchant-state/ mid-flight orphaned 0.05 RLUSD — paid, never delivered. Re-run the agent with the same operation name instead: node x402-agent.mjs <operation>.

If the merchant was killed rather than interrupted, it leaves merchant.lock behind and refuses to start. Delete the lock — never merchant.sqlite.

Give every purchase a new operation name

Reusing one returns the earlier purchase instead of buying again, which on stage looks like a payment that silently did nothing. The agent generates a fresh name on each run; only pass one explicitly when you are deliberately resuming.

What we have not done

Say this plainly if asked. It is a better answer than being caught out.

  • No cross-team payments. AP4M returns an empty merchant list; the organizers have not enabled it.
  • The merchant is localhost only. It binds 127.0.0.1. Reaching it from another machine needs HTTPS, so the agent and the merchant run on the same laptop.
  • Small amounts only. The largest single payment is 0.05 RLUSD against a 20 RLUSD budget. Nothing has been pushed near the channel cap or a minimum.
  • One base unit below the ceiling was not run. Equal and one-above were, which is the pair that decides the comparison. The run below the limit would add nothing but completeness.
  • Three edits to the vendor helper. ap4m-x402.mjs came from the service and did not run here unmodified: a directory fsync that Windows refuses, a verification that raced its own submission, and the error logging above. All three are commented in the file and written up in X402.md. Say so if asked — it is a finding worth reporting to the organizers, not something to hide.
  • Only one merchant, selling one thing. There is no catalogue, no price negotiation and no second seller to choose between.

If something breaks mid-demo

  • Preflight fails. Read what it says — it names the exact problem. Do not re-run hoping.
  • Channel hangs at "requested". The SDK polls for three minutes. Let it; it usually resolves.
  • RPC times out. Transient and common under event load. Re-run. It is not a failure of the payment.
  • The merchant 503s. Look at terminal 1 for the logged cause. Then re-run the agent with the same operation name — a retained payment replays and delivers. Do not wipe state.
  • The merchant will not start. Stale merchant.lock. Delete it, keep the database.
  • Everything is broken. Fall back to the receipt trail. The payments already happened and are permanently on chain — the evidence does not depend on anything working in the room.
