AP4M Walkthrough

What we built, how to run it, and what to say while it runs. Read this once before demoing; the commands are set apart so you can find them at a glance.

The one-sentence version

An autonomous agent holds its own wallet, signs a payment voucher without a human in the loop, redeems it against a settlement contract, and the money lands in a merchant wallet — and anyone can verify that it happened without trusting us or the payment service.

The pieces

Pays Agent wallet Signs every voucher. Holds XRP for gas.
Holds funds Escrow vault Our 20 RLUSD budget sits here.
Records PaymentLedger Verifies the signature, emits the claim.
Receives Merchant wallet Gets the RLUSD. Ours, not a pool.

Two wallets, and they must be different addresses — AP4M rejects a setup where the party authorising a payment is also the party receiving it. That separation is the point, not a formality.

Before you demo

Run this first. It talks to AP4M but spends nothing, so it is safe to run in front of people and it catches every setup problem we hit:

node verify-wallets.mjs

It exits 0 only when the agent key matches the address AP4M has registered, the agent has gas, and the agent and merchant are different wallets. If it exits non-zero, do not start the demo — fix what it names.

node signin-check.cjs

Confirms the service side is up and our team session still authenticates. Also free.

Check the gas before you stand up

Each full run costs roughly 0.0003 XRP. The agent had about 20 XRP, which is hundreds of runs — but the faucet is rate-limited and slow during the event, so top up the night before rather than in the room.

Running it

node run-ap4m.cjs

One command, six steps, about twenty seconds. It pays 0.01 RLUSD by default — set PAYMENT_RLUSD in .env to change it. Each run opens a fresh channel and closes it at the end, so you can run it repeatedly without cleanup.

What to say while it runs

1 — Sign in

The agent wallet signs a one-time challenge. No password, no API key issued by a human.

"The agent authenticates as itself. Nobody logged in for it."

2 — Open a channel

One on-chain transaction to the vault, with a spending cap of 5 RLUSD.

"This is the agent's allowance. It cannot spend past the cap, whatever it decides to do."

3 — Sign and redeem a voucher

An EIP-712 typed signature over the channel and a running cumulative total, submitted to the PaymentLedger.

"The signature is bound to this chain and this contract, so the same voucher cannot be replayed somewhere else."

4 and 5 — Report and settle

The service releases RLUSD from the vault to our merchant wallet and publishes a receipt.

"The money has moved. Here is the receipt — and we don't have to take their word for it."

6 — Close the channel

The agent signs a final checkpoint and the channel closes.

"The allowance is withdrawn. Nothing is left open."

The verification half

This is the part worth the most in judging, because it is the part that does not require trusting anyone. Open the receipt trail — it puts AP4M's claims beside the ledger's own emitted events and shows them matching.

To do it live instead, with the judge choosing the node:

RPC_URL=<their node> node verify-receipt-onchain.mjs <redemption tx>

It confirms the transaction succeeded, that it went to the PaymentLedger, decodes the claim and channel IDs out of the event log, and finds the RLUSD transfer into the merchant wallet in the surrounding blocks.

The line that lands

"The receipt isn't us telling you we paid. It's the ledger telling you, and you can read it from a node we've never touched."

Traps — read these before demoing

Portal identifiers are claim IDs, not transaction hashes

The identifiers under Payments and receipts return null from eth_getTransactionByHash. Pasting one into a block explorer on stage gives you an empty page and looks like a failed payment. Use the transaction hashes from the agent wallet's history instead.

MetaMask exports private keys without the 0x prefix

Pasted straight into .env, the key is rejected as invalid — which reads like the wrong key rather than a formatting problem. Prefix it.

AP4M's own config points at a faucet that does not exist

/public/config advertises faucet.testevm.ripple.com, which returns NXDOMAIN. The working one is faucet.xrplevm.org. Worth mentioning to the organizers — it is costing every team the same half hour.

Gas and the payout wallet are two separate blockers

Funding the agent is not enough. requestChannel() binds a merchant payout when it opens, so the payout wallet must be registered on the portal first or the run fails at step 2.

What we have not done

Say this plainly if asked. It is a better answer than being caught out.

  • One payment per channel. Every run so far opened and closed its own channel. Multiple vouchers on a single open channel — the actual micropayment case — is untested.
  • No cross-team payments. AP4M returns an empty merchant list; the organizers have not enabled it.
  • Demo 2 (x402 over HTTP) not run. We did the SDK path only.
  • Small amounts only. Two payments of 0.01 RLUSD against a 20 RLUSD budget. Nothing has been pushed near a cap or a minimum.

If something breaks mid-demo

  • Preflight fails. Read what it says — it names the exact problem. Do not re-run hoping.
  • Channel hangs at "requested". The SDK polls for three minutes. Let it; it usually resolves.
  • RPC times out. Transient and common under event load. Re-run. It is not a failure of the payment.
  • Everything is broken. Fall back to the receipt trail. The payments already happened and are permanently on chain — the evidence does not depend on anything working in the room.
